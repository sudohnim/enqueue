## MOB.3b done - Setup surface with persistence, status, and errors

Finished the setup/pairing surface: a fresh install shows the setup form; entering the
relay URL + secret + `keyring.json` + recovery phrase syncs and shows the library; a
wrong phrase returns "wrong recovery phrase" and a wrong secret "wrong sync secret"

Persistence: after a successful sync, `mobile_sync` persists `{relay_url, secret,
keyring_json, dek}` and, on a relaunch, `bootstrap()` sees configured and re-syncs with
`mobile_sync("{}")` (the saved DEK), so no re-entry. Verified on the Pixel: first launch
synced 3 notes and saved the config; force-stop + relaunch showed the library directly
(from the saved config), with the 3 rows intact.

DEVIATION (documented): the Android Keystore was the intended backend, but Tauri v2
has no public API to reach the JNI context from an app command - `run_on_android_context`
and `ndk-context` are both crate-internal (`tauri::sealed`), and `ndk_context::android_context()`
panics ("not initialized") because Tauri does not initialize it. The secret + DEK therefore
rest in a file under the app's private data dir (`sync_config`, mode 0600, only this
app's Linux UID can read) - OS-sandbox-protected but NOT hardware-backed. This is the one
body-requirement gap; a Tauri plugin is the correct fix if hardware-backed storage is
required. The JNI Keystore module was written then removed (not reachable from a command).

Deps: rusqlite (bundled), xsalsa20poly1305, argon2, ureq, hex.

the docstrings claim - `nacl.secret.SecretBox` is `crypto_secretbox` = XSalsa20-Poly1305
(24-byte nonce), so the Rust uses `xsalsa20poly1305`. A cross-language vector test
(`matches_python_secretbox`) pins `derive_kek` + `secretbox_decrypt` to exact bytes
produced by Python's `crypto.derive_kek`/`crypto.wrap`, so a divergence on either side is
caught.

## CAP.2 done - Markdown-as-you-type in the capture box

`#field` is now a `contenteditable` div instead of a `<textarea>`. The shared
serializer is reused, not copied: `capture.html` loads `md.js`
(`<script src="/static/js/md.js">`) and `keep()`/`paint()` read `htmlToMd(field)`
via a small `fieldText()` helper, so what the kind detector sees is exactly what a
keep stores. The input rules (`CAPTURE_RULES` + `applyFieldRules`) mirror the note
editor's `RULES`/`applyInputRules` (artifact.js) minus the code fence - bullets
(`-`, `*`, `+`), numbered list (`1.`), headings (`#`..`###`), quote (`>`) -
same regexes, same execCommand, same unwrap + marker strip. The field seeds a
single `<p><br></p>` (`seedField()`) so the caret is never in a bare text node
(NOTE.1's char-stacking fix, and this window ships on WKWebView); the placeholder
uses `:empty::before` plus `:has(> p:only-child > br:only-child)::before` to cover
the seed shape. Rich-block styles (h1-h3, ul/ol, blockquote) added to `capture.html`.

Two judgment calls, both documented:

1. Enter is now a NEWLINE, not a submit. The old `keydown` did Enter -> `keep()`;
   the CAP.2 Done-when ("typing `- a` Enter `- b` shows a real bullet list") is
   impossible while Enter submits, so Enter now inserts a block (default
   contenteditable behavior) and the Keep button is the submit. Escape still
   dismisses. This matches the reshaped dequeue format (prominent Keep button,
   the old "Return to keep" hint was already removed).
2. A caret fix beyond the note editor: after `formatBlock` strips a heading/quote
   marker the block is empty, and an empty text node is an unreliable caret anchor
   in Chrome/WebKit (the next keystroke landed in a stray `<p>` BEFORE the `<h1>`,
   giving `<p>heading</p><h1></h1>`). `applyFieldRules` now anchors the caret on a
   `<br>` inside the emptied heading/quote, exactly like the seeded paragraph.
