## Phase J1 - longer notes render broken in the preview cards

On the wall, a note card whose body is long or markdown-heavy renders as overlapping, garbled text (observed on "Stone Philosophy Book" and a "##"-titled note: headings and bullets overlap each other inside the card).
The card excerpt renders full markdown into a fixed, clamped box, and multi-line markdown - `##` headings, nested bullets - overflows and paints over itself.

- [x] **J1.1 [AGENT]** Make the note preview excerpt a clean, clamped snippet that cannot overlap.
  Anchor: `card(a, i)` in `src/enqueue/static/museum.html` (around line 3808), where a note's excerpt is rendered with `md(a.excerpt || "")` (around 3851), and the `.excerpt` CSS (around 477).
  The fix is a decision, not a nudge: a preview card should show a short plain-text snippet, not rendered markdown headings and bullet nesting, so either strip markdown to text before clamping, or render into a strict `line-clamp` + `overflow: hidden` box whose height cannot grow.
  Whichever path, a `##` heading or a nested list must never paint outside the card or over another line.
  Verify: on the desktop, a long multi-heading note (for example "Master of the Senate" or "The Stone Reader") shows a clean, truncated preview with no overlap at mobile, tablet, and desktop widths.

## Phase J2 - "That answer could not be completed." on ordinary questions

Asking a normal question frequently returns the failed-turn text "That answer could not be completed." - which is `FAILED_TEXT` written by the async worker's except block when its compute throws.
So the answer worker is raising on ordinary questions; this is a real bug, not a display issue, and it must be diagnosed before it is patched.

- [x] **J2.1 [AGENT]** Reproduce and capture the underlying exception.
  Anchor: `src/enqueue/chats_worker.py::compute` (the `try` around route plus `REGISTRY[skill].run`, whose except writes `status='failed'` and `FAILED_TEXT`), and the answer path it calls: `chats.run_answer` -> `chats.passages` -> `_ask_model`, plus the retrieval changes from Phase I (the entity branch in `retrieve/candidates.py`, `hit_is_stale`) and the active provider (currently OpenRouter/Gemini).
  Reproduce by asking a plain question through the running engine, then read the engine log - the worker logs the full exception - and identify the exact throw.
  Do not widen the except or swallow the error; find the line that raises.
  Verify: the engine log shows the concrete exception and traceback for a failing question.

- [x] **J2.2 [AGENT]** Fix the cause the log points to.
  The likely suspects, in order: an exception inside `run_answer` from the new entity/facet retrieval or `hit_is_stale`, a provider/schema error from the Gemini path, or a router failure - but let J2.1's log decide, not this guess.
  Verify: ask "do I have notes on presidents" and two other plain questions through the app; each returns a real answer, and the engine log shows no worker exception.

- [ ] **J2.3 [HUMAN]** Confirm on the desktop that ordinary questions answer normally and the failed-turn text no longer appears for healthy questions.
